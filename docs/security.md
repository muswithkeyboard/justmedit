# Безопасность и персональные данные

Документ описывает, что сделано в прототипе, и отдельно — чего в нём нет. Прототип не предназначен
для работы с данными пациентов. На странице демо так и написано: не вводите персональные данные.

## Пять рисков и пять мер

| Риск | Мера в прототипе | Где в коде |
|---|---|---|
| Утечка данных из хранилища | Без входа хранилища нет: сервис ничего не сохраняет. В личном кабинете (ADR 0009) значения анализов, ответы и референсы в базе зашифрованы, пароли — scrypt, токены — только SHA-256 | `service.py`, `engine.py`; `store.py`, `auth.py` |
| Данные в журнале | В журнал пишутся только время, метод, путь, код ответа и длительность | `security.py`, `SecurityMiddleware` |
| Чужой доступ к API | Ключ в заголовке `X-API-Key`; без ключа 401, с неверным 403 | `security.py`, `check_api_key` |
| Перегрузка и слишком большие запросы | Пределы размера тела, файла и пакета; лимит запросов для страницы демо | `security.py`, `settings.py` |
| Передача данных третьим лицам | Сервис никуда наружу не обращается; страница не грузит внешних ресурсов, кроме подложки карты «Где сдать рядом» по кнопке (без координат и значений анализов, ADR 0008) | весь `src/` |

## Что сервис не хранит (без входа)

Всё в этом разделе — о работе без входа: страница демо, `/ui/*`, `/api/v1/analyze|batch|benchmark|parse|columns`.
Личный кабинет хранит данные по согласию — см. раздел «Личный кабинет» ниже.

- Базы данных для расчётов без входа нет: база кабинета открывается только при обращении к кабинету.
- Запросы и ответы на диск не пишутся.
- Модели и конфигурация только читаются.
- Файл, загруженный в `/api/v1/benchmark`, `/api/v1/columns`, `/api/v1/parse` или на страницу демо, разбирается в памяти
  и на диск не пишется (форма читается из уже полученного тела, без сброса во временный файл). PDF бланка
  разбирается в отдельном дочернем процессе с таймаутом; текст передаётся ему через стандартный ввод.
  В контейнере единственный каталог для записи `/tmp` — это `tmpfs`, то есть память, а не диск.
- Фото бланка (ADR 0007) распознаётся локальным Tesseract в дочернем процессе: фото — через стандартный ввод,
  pytesseract кладёт картинку и результат во временные файлы только в `/tmp` (`TMPDIR=/tmp`, в контейнере
  `tmpfs`) и удаляет их сразу после распознавания. Перед распознаванием создаётся новая картинка в оттенках
  серого без метаданных: EXIF (модель телефона, время, GPS) не попадает ни во временный файл, ни в ответ.
- Между запросами в памяти процесса остаются только счётчики лимитов: для страницы демо — адрес клиента
  и отметки времени запросов за последнюю минуту; для тяжёлых запросов `/api/v1/*` — первые 16 знаков
  SHA-256 ключа (не сам ключ) и отметки времени.

Для расчёта нужны пол, возраст в годах и значения анализов. ФИО, дата рождения, номер полиса, телефон
и адрес сервису не нужны, и полей для них в API нет: лишнее поле в запросе — ошибка 422.
Поле `patient_ref` — произвольная метка строки. Сервис возвращает её как есть и не сохраняет.
Не кладите в неё персональные данные.

Разбор бланка (`/api/v1/parse`: вставленный текст или файл — фото, PDF с текстом или скан, TXT, CSV / XLSX
одного анализа) возвращает распознанные показатели, нормы с бланка и дату анализа. Пол, возраст и ФИО из текста
не извлекаются; из дат берётся только дата анализа с подписью («Дата взятия / выполнения / регистрации / выдачи»
или «Дата:»), дата рождения — никогда.
Нераспознанные строки возвращаются только номером и причиной («строка 9: название показателя не распознано»),
без текста бланка: ФИО, телефон, полис или СНИЛС из соседних строк в ответ не попадают.
С фото — то же: распознанный текст (в нём ФИО, дата рождения, телефон с шапки бланка) разбирается тем же
разбором текста и в ответ не возвращается; дополнительно приходят только `warnings` («строка 6: Ферритин —
проверьте значение») и `check` (коды показателей) для строк, где Tesseract не уверен в цифрах. Расчёт по фото
сам не запускается: значения заполняют форму, пользователь сверяет их и нажимает «Рассчитать».
Распознанный текст и значения в журнал не пишутся (тест `tests/api/test_photo_api.py`).

## Личный кабинет: что хранится, шифрование, удаление, сессии, CSRF, CORS, модель угроз

Решение — ADR 0009, маршруты — `docs/CONTRACTS.md` («Хранение и кабинет»), код — `src/deficitlens_api/store.py`,
`auth.py`, `cabinet_api.py`, тесты — `tests/api/test_cabinet.py`. Это прототип: в кабинет не вводите реальные данные.

### Что хранится и где

База SQLite `justmedit.db` в каталоге `DL_DATA_DIR` (по умолчанию `data/app/` в репозитории — в `.gitignore`;
в Docker — том `jm-data`, смонтированный в `/data`; остальная файловая система контейнера только для чтения).
Файлы базы и ключа создаются с правами `0600`. Без входа база не открывается и не создаётся.

| Таблица | Открытым текстом | Зашифровано |
|---|---|---|
| `users` | логин (и он же в нижнем регистре для поиска), роль, клиника врача, дата согласия и регистрации | — (пароль: только хэш scrypt) |
| `sessions` | SHA-256 токена, вид (cookie сайта / токен API), имя токена, сроки | — (самих токенов в базе нет) |
| `records` | дата анализа, источник (форма, фото, PDF, файл, загрузка), версия движка, время записи | вход анализа (`AnalysisInput`) и ответ движка; сводка: заголовки отчётов, анемия да/нет |
| `shares` | кто кому открыл доступ, срок, когда принят и отозван; SHA-256 одноразового токена ссылки | — |
| `access_log` | какой врач, когда, что открывал (история или запись) | — (содержимого нет) |
| `lab_refs` | имя набора референсов врача, «по умолчанию» | границы референсов |

Открыто только то, что нужно для поиска и связей. Значений анализов, текстов отчётов, `patient_ref`
в файле базы открытым текстом нет (тест ищет приметные числа и строки в байтах `*.db`, `*-wal`, `*-shm`).

### Шифрование

- Fernet из библиотеки `cryptography` (AES-128-CBC и HMAC-SHA256, случайный IV на каждое поле).
  Перед шифрованием JSON сжимается zlib.
- В открытый текст каждого поля входит его «привязка» — таблица, id строки и владелец: поле, перенесённое
  в чужую строку, не расшифруется (ошибка `storage_key`, без содержимого).
- Ключ — переменная `DL_DATA_KEY` (urlsafe base64 от 32 байт). Можно несколько через запятую: первый шифрует,
  остальные только расшифровывают — так ключ меняется без потери данных.
- Нет `DL_DATA_KEY` — при первом обращении к кабинету ключ создаётся файлом `<DL_DATA_DIR>/key` (`0600`),
  в журнал пишется одна строка-предупреждение (путь, без ключа). Ключ рядом с базой защищает только от утечки
  самого файла базы — это режим демо.
- **Вне демо ключ обязателен и не лежит в томе с базой**: `DL_DATA_KEY` из хранилища секретов или файл-секрет
  `DL_DATA_KEY_FILE` (секрет Docker, смонтированный только для чтения вне `/data`). Файл с правами шире `0600`
  (его читают группа или все) не принимается — `503 storage_unavailable`; файл ключа внутри `DL_DATA_DIR` —
  предупреждение в журнале. Заданы и `DL_DATA_KEY`, и `DL_DATA_KEY_FILE` — отказ (`503`), чтобы не гадать, какой
  из них действует.
- Неверный ключ — `503 storage_unavailable`; ключ не от этой базы — `500 storage_key`. Расчёты без входа
  от кабинета не зависят и продолжают работать.

### Пароли и вход

- `hashlib.scrypt`: n = 2^14, r = 8, p = 1, 32 байта, соль 16 байт; формат `scrypt$n$r$p$соль$хэш`;
  сравнение — `hmac.compare_digest`.
- Логин — 3–64 символа (латиница, кириллица, цифры, `._-@`), без учёта регистра. При регистрации латиница
  и кириллица в одном логине не смешиваются (`ivаn` с кириллической «а» выглядит как `ivan` — 422); логины,
  заведённые раньше, входят как прежде. Пароль — 8–128 символов. Регистрация — только с `consent: true`.
- Неверный логин и неверный пароль дают одинаковый ответ `401 «Неверный логин или пароль.»`; для неизвестного
  логина считается scrypt от фиктивного хэша, поэтому и время ответа одинаковое.
- Лимит попыток входа, регистрации, удаления аккаунта, смены пароля и подтверждения паролем: 10 в минуту на пару
  «адрес + логин» и 60 в минуту на адрес (`429` с `Retry-After`). Логин в памяти лимитера хранится только как
  начало SHA-256.
- Общий счётчик неудач на логин — с любых адресов (перебор с многих адресов лимит «адрес + логин» не ловит):
  после 10 неудач за 15 минут логин на паузе 1 минуту (`429`, и для верного пароля), каждая следующая пауза вдвое
  длиннее, не больше 15 минут; после 15 минут без неудач — снова с 1 минуты. Навсегда не блокирует. Счёт ведётся
  и для несуществующих логинов — по ответу не узнать, есть ли логин.
- Регистраций — не больше `DL_SIGNUP_IP_PER_HOUR` (30) в час с одного адреса (неудачная — не в счёт) и не больше `DL_MAX_SIGNUPS_PER_DAY`
  (1000) в сутки на весь сервис (`503 signups_paused`; считаются по базе — перезапуск не обнуляет).
- Адрес для всех лимитов — адрес соединения; IPv6 — сеть `/64` (у абонента обычно целая `/64`). Заголовки
  `X-Forwarded-For`, `-Proto`, `-Host` учитываются только от прокси из `DL_TRUSTED_PROXIES` (по умолчанию —
  ни от кого): адрес клиента — первый справа адрес цепочки, который сам не доверенный прокси. Uvicorn свои
  заголовки прокси не разбирает (`--no-proxy-headers` в `Dockerfile`, `Makefile`, `scripts/verify.sh`):
  по умолчанию он доверял бы им от `127.0.0.1`.
- Регистрация открывает, что логин занят (`409 login_taken`): для демо это допустимо, лимит не даёт перебирать.

### Сессии и токены

- Сайт — cookie `jm_session`: `HttpOnly; SameSite=Strict; Path=/; Max-Age=604800` (7 дней). За HTTPS
  (`DL_COOKIE_SECURE=1`, включайте его всегда, когда сайт открыт по HTTPS) — `__Host-jm_session` с `Secure`:
  браузер примет такую cookie только с `Secure`, `Path=/` и без `Domain` — её не подставит поддомен и не поставит
  страница по HTTP. Локально по HTTP (`DL_COOKIE_SECURE=0`) — прежнее имя без `Secure`.
- Внешние сайты и программы — `Authorization: Bearer <токен>`. Токен входа «Вход» приходит в ответе на вход
  и регистрацию и живёт столько же, сколько cookie этого входа (7 дней): выход на сайте или истечение cookie
  закрывают оба. Именованные токены (`/api/v1/me/tokens`) — 30 дней; созданный по Bearer-токену — не дольше
  этого токена. Значение показывается только один раз. Cookie принимается только как cookie, токен API — только
  как Bearer.
- Токен — `secrets.token_urlsafe(32)`; в базе только SHA-256. Просроченный токен не принимается (`401`) и удаляется.
- Пределы: входов (cookie + её токен «Вход») — 20, сверх вытесняются самые старые; именованных токенов — 20,
  сверх — `422 too_many_tokens`, старые молча не удаляются (это могут быть токены интеграций).
- **Область токена API.** Bearer может: анализ (`/api/v1/analyze|batch|benchmark|parse|columns|reference`),
  чтение кабинета, запись и удаление анализов, загрузку выгрузки, отзыв токенов и ссылок, принятие ссылки врачом,
  референсы врача. Создать новый токен, ссылку врачу и «выйти везде» по Bearer можно только с паролем аккаунта
  в теле (`password`; нет — `403 password_required`, неверный — `403 wrong_password`, с лимитами входа):
  украденный токен не размножается, не продлевается и не открывает историю постороннему «врачу». Сессии сайта
  (вход с паролем, cookie HttpOnly + CSRF) пароль повторно не спрашивают. Удаление аккаунта и смена пароля —
  всегда с паролем.
- `POST /api/v1/me/logout-all` — отозвать все сессии и токены, кроме текущего входа (`{"all": true}` — и его).
  `POST /api/v1/me/password {old, new}` — смена пароля; все остальные сессии и токены, в том числе именованные,
  отзываются.

### Защита от подделки запроса (CSRF)

Изменяющий запрос (`POST`, `PUT`, `PATCH`, `DELETE`), авторизованный cookie, принимается только если:

1. есть заголовок `X-Justmedit: 1` — чужой сайт не может добавить его без разрешения CORS, а CORS для cookie
   не включается никогда;
2. `Origin` (если браузер его прислал) — наш источник: схема, хост и порт совпадают с адресом запроса
   (`Host`; схема и хост от доверенного прокси — из `X-Forwarded-Proto` и `X-Forwarded-Host`, от остальных эти
   заголовки не учитываются); если `Origin` нет — то же для `Referer`. Одно послабление: запрос пришёл по HTTP,
   а `Origin` — `https://` с тем же хостом без явного порта (TLS снят прокси, не указанным в
   `DL_TRUSTED_PROXIES`); обратное (запрос по HTTPS, `Origin` по HTTP) отклоняется. `Origin: null` (страница
   с `Referrer-Policy: no-referrer`, песочница) считается отсутствующим: тогда защиту держат пункт 1
   и `SameSite=Strict`.

Иначе — `403 {"error":{"code":"csrf"}}`. Запросы с Bearer-токеном от CSRF не зависят (браузер сам его не
подставляет). Тела JSON кабинета принимаются только с `Content-Type: application/json` (иначе `415`): простая
HTML-форма с чужого сайта так не отправляется — это закрывает и подделку входа.

### CORS

Только для `/api/v1/*` и только источникам из `DL_CORS_ORIGINS` (точное совпадение «схема://хост:порт»;
`*` не поддерживается): `Access-Control-Allow-Origin` — этот источник, `Vary: Origin`, без
`Access-Control-Allow-Credentials`. Предварительный запрос: методы `GET, POST, PATCH, DELETE`, заголовки
`Authorization, Content-Type, X-API-Key`, `Max-Age 600`; чужой источник — `403` без заголовков CORS.
Маршруты анализа `/api/v1/analyze|batch|benchmark|parse|columns|reference` принимают `X-API-Key` или Bearer-токен
пользователя. Ключ API на чужой странице — это публичный ключ; для внешних сайтов лучше Bearer-токен
пользователя или запрос с сервера сайта.

### Доступ врача

- Только врачу с аккаунтом и только по одноразовой ссылке `/share#<токен>`: фрагмент после `#` не уходит на
  сервер и в журнал, страница отправляет токен `POST /api/v1/shares/accept`. Токен живёт 48 ч до принятия,
  после принятия его хэш стирается — второй раз ссылка не сработает (`404 share_invalid`).
- Связь — 1, 7, 30 или 90 дней с момента принятия; пациент отзывает её в любой момент (`DELETE
  /api/v1/me/shares/{id}`), доступ закрывается сразу. Нет действующей связи — `403` (и для чужого, и для
  несуществующего пациента: перебором id не узнать, есть ли такой пациент).
- Каждое открытие истории, списка записей (`/api/v1/doctor/patients/{id}/records`) или записи пациента врачом
  пишется в `access_log`; пациент видит журнал
  (`/api/v1/me/access-log`): кто (логин и клиника), что и когда. Повторы «врач — что» в течение часа — одна
  строка (журнал не растёт от обновления страницы); если за этот час открывались разные записи, `record_id`
  строки — `null`.
- Список пациентов врача (`/api/v1/doctor/patients`) значений не показывает: `last_headline` — только «есть ли
  анемия по последнему анализу», без чисел и выводов движка. Значения врач видит, открыв запись или историю, —
  и это попадает в журнал пациента.
- Референсы лаборатории врача («по умолчанию») подставляются в `/api/v1/analyze` и `/ui/analyze`, только если
  запрос сделал врач и в запросе нет своих `reference_ranges`. В ответе — обычное предупреждение о локальных
  референсах.

### Удаление

`DELETE /api/v1/me` с паролем: в одной транзакции удаляются пользователь, его сессии и токены, записи, связи
(и как пациента, и как врача), журнал доступа к его данным, его референсы. `secure_delete=ON` затирает удалённые
строки нулями прямо при удалении; затем свободные страницы отдаются ОС порциями `incremental_vacuum` (по 64
страницы; общий замок берётся на каждую порцию, другие запросы идут между ними; база создаётся с
`auto_vacuum=INCREMENTAL`) и WAL усекается (`wal_checkpoint(TRUNCATE)`). Полного `VACUUM` нет: он переписывал всю
базу под общим замком, и одно удаление аккаунта останавливало кабинет для всех. Тест после удаления ищет логин
и id пользователя в байтах файлов базы — их нет, и проверяет, что полного `VACUUM` не было. WAL усекается и после
удаления отдельной записи (`DELETE /api/v1/me/records/{id}`), отзыва ссылки и удаления набора референсов — тест
ищет шифртекст удалённой записи в файлах базы и WAL. В журнале доступа других пациентов строка об удалённом враче
остаётся без ссылки на него («врач удалил аккаунт»): это данные пациента. Резервных копий нет (их нет и для
восстановления). Стереть всё сразу в Docker: `docker compose down -v`.

Чего это не даёт: усечение файла и затирание страниц работают на уровне файла; файловая система, SSD
(перераспределение блоков), снимки тома и резервные копии хоста могут хранить старые блоки. Для настоящего
стирания — шифрование тома и уничтожение ключа (`DL_DATA_KEY`) вместе с томом.

### Пределы (защита от переполнения диска и перегрузки)

| Что | Предел | Ответ |
|---|---|---|
| Вход одной записи анализа после проверки (JSON) | 16 КБ; показатели — только известные коды и названия; `patient_ref`, `lab_reference` — до 64 символов; `provenance` не хранится | `413 record_too_large`, `422 unknown_analyte` / `invalid_value` |
| Данные одного пользователя (шифртекст записей и наборов референсов) | 5 МБ и 500 записей | `422 quota_exceeded`, `422 too_many_records` |
| Размер базы | `DL_DATA_MAX_MB` (512) | `507 storage_full` на новые записи, наборы, ссылки и регистрации; вход, чтение, выгрузка и удаление работают |
| Регистрации | `DL_SIGNUP_IP_PER_HOUR` (30) в час с адреса (IPv6 — `/64`), `DL_MAX_SIGNUPS_PER_DAY` (1000) в сутки | `429`, `503 signups_paused` |
| Загрузка выгрузки (`/api/v1/me/import`) | сначала проверка всех записей без расчёта, потом расчёт под слотом тяжёлых расчётов; `DL_UI_RATE_PER_MIN` в минуту на пользователя (общий счёт с `/api/v1` batch, benchmark, columns, parse) | `422`, `503 service_busy`, `429` |
| История (`/api/v1/me/history`, история пациента у врача) | под слотом тяжёлых расчётов | `503 service_busy` |
| Вложенность JSON (кабинет и маршруты анализа) | 32 уровня; глубже, в том числе такая, на которой разборщик падает с `RecursionError` | `422 invalid_json` |
| Тексты для показа (клиника, имя набора референсов — и из имени файла, имя токена) | одна проверка: длина, без управляющих, форматных (смена направления текста, невидимые) символов и разделителей строк | `422` |
| Запросов кабинета на пользователя | 240 в минуту | `429` |

### Журнал сервера

Как и без входа: метод, путь, код, длительность. Логинов, паролей, токенов, тел запросов и значений в журнале нет;
id записей и пациентов в пути — допустимы (тест `test_log_has_no_logins_tokens_or_values`).

### Модель угроз (кратко)

| Угроза | Мера | Чего мера не даёт |
|---|---|---|
| Утечка файла базы или тома | Значения анализов, ответы, референсы зашифрованы; пароли — scrypt; токены — SHA-256; вне демо ключ — `DL_DATA_KEY` или `DL_DATA_KEY_FILE` вне тома (права `0600`) | Логины, роли, клиники, даты анализов и связи видны; при демо-ключе рядом с базой утечка всего тома раскрывает и данные |
| Остатки удалённого на диске | `secure_delete`, усечение WAL после каждого удаления, отдача свободных страниц ОС | Файловая система, SSD, снимки тома и резервные копии хоста могут хранить старые блоки — нужно шифрование тома |
| Подбор пароля | scrypt; лимит на адрес и «адрес + логин»; общий счётчик неудач на логин с нарастающей паузой | Злоумышленник может держать чужой логин на паузе (до 15 мин за раз), пока перебирает: вход владельца в это время — `429`; открытые сессии работают |
| Подмена адреса для обхода лимитов | `X-Forwarded-For` — только от `DL_TRUSTED_PROXIES`, uvicorn с `--no-proxy-headers`; IPv6 — по `/64` | За прокси без `DL_TRUSTED_PROXIES` все клиенты делят адрес прокси (лимит общий); владелец многих сетей `/64` или IPv4-адресов лимит по адресу обходит — его держат лимиты на логин и пользователя |
| Перебор логинов | Одинаковый ответ и время на входе; пауза входа и для несуществующего логина | Регистрация говорит «логин занят» |
| Похожие логины (подмена врача) | Латиница и кириллица в одном логине не смешиваются | Логины целиком на разных алфавитах (`ivan` и `іван`) различимы только по виду; клиника — свободный текст |
| Кража cookie через XSS | `HttpOnly`, CSP без встроенных скриптов, вставка данных на страницу только как текст; за HTTPS — `__Host-` и `Secure` | Токен «Вход» из ответа на вход доступен скрипту страницы (живёт 7 дней, отзывается выходом) |
| Украденный токен API | Без пароля токен не создаёт новых токенов и ссылок врачу; дочерний токен не живёт дольше родителя; «выйти везде» и смена пароля отзывают всё | До отзыва или срока токен читает кабинет и меняет записи; именованный токен живёт 30 дней |
| Подделка запроса с чужого сайта (CSRF) | `X-Justmedit`, сверка схемы, хоста и порта `Origin`/`Referer`, `SameSite=Strict`, только `application/json` | Запрос по HTTP с `Origin: https://тот-же-хост` принимается (TLS на прокси вне `DL_TRUSTED_PROXIES`) |
| Чтение API чужой страницей | CORS только для `DL_CORS_ORIGINS`, без credentials | Серверы (не браузеры) CORS не ограничивает — для них нужен токен или ключ |
| Доступ врача без разрешения | Одноразовая ссылка с 256-битным токеном (по Bearer — только с паролем), срок, отзыв, журнал доступа | Принятую ссылку врач может использовать до конца срока; пациент видит это в журнале (повторы за час — одной строкой) |
| Подмена зашифрованного поля в базе | Привязка поля к таблице, строке и владельцу | Удаление строк злоумышленником с доступом к базе не обнаруживается |
| Переполнение диска | 16 КБ на запись, 5 МБ и 500 записей на пользователя, `DL_DATA_MAX_MB` на базу, регистрации — `DL_SIGNUP_IP_PER_HOUR` (30) в час с адреса и `DL_MAX_SIGNUPS_PER_DAY` в сутки | Ботнет может заполнить суточный предел регистраций и базу до `DL_DATA_MAX_MB`: дальше новые регистрации и записи закрыты для всех (`503`/`507`) до очистки |
| Перегрузка | Лимит запросов кабинета на пользователя; история и загрузка — под слотом тяжёлых расчётов; загрузка ещё и в лимите тяжёлых запросов; без полного `VACUUM` под общим замком; глубокий JSON — `422` | Лимиты — в памяти одного процесса (перезапуск их обнуляет, несколько процессов — у каждого свои); слот тяжёлых расчётов общий — занятый слот даёт `503` и истории |

## Что сервис не пишет в журнал

Строка журнала: время, метод, путь, код ответа, длительность. Журнал идёт в поток ошибок процесса.

В журнал не попадают:

- тела запросов и ответов;
- строка запроса (то, что после `?`);
- значения анализов, метка `patient_ref`, ключ API;
- адрес клиента.

При внутренней ошибке клиент получает `500` и текст «Внутренняя ошибка» без трассировки. В журнал пишутся
только тип исключения и место в коде (файл и строка) — без текста исключения, потому что в нём могут быть
значения анализов.

Журнал самого uvicorn (access log) в `Dockerfile` и `Makefile` выключен флагом `--no-access-log`:
он писал бы адрес клиента и строку запроса.

Проверка: `scripts/verify.sh` отправляет запрос с приметной меткой и приметным значением гемоглобина,
а затем ищет их и ключ API в журнале сервера.

## Ключ API

- Маршруты анализа `/api/v1/*` требуют заголовок `X-API-Key` или токен кабинета `Authorization: Bearer <токен>`
  (ADR 0009). Нет ни того, ни другого — `401`, неверный ключ — `403`, неверный или просроченный токен — `401`.
  Лимит тяжёлых запросов для токена считается на пользователя.
- Ключи задаются переменной окружения `DL_API_KEYS`, через запятую.
- Если переменная пуста, при старте создаётся случайный ключ и печатается в стандартный вывод одной строкой
  `DL_API_KEY=<ключ>`.
- Сравниваются SHA-256 ключей функцией `hmac.compare_digest`, по всем ключам без раннего выхода:
  время проверки не зависит от длины и содержимого ключа.
- В `docker-compose.yml` по умолчанию стоит демо-ключ `dl-demo-key`. Он известен всем, кто видел репозиторий.
  Для любого использования вне демо задайте свой: `DL_API_KEYS=<ключ> docker compose up`.

Маршруты `/ui/*` обслуживают страницу демо и ключа не требуют. Вместо ключа у них лимит запросов
на адрес клиента. `/healthz`, страницы и статика тоже открыты.

## Лимиты

| Что | Значение по умолчанию | Настройка |
|---|---|---|

Справочник `GET /ui/reference`, `/ui/examples` — статичные данные конфигурации: без лимита, `Cache-Control: public, max-age=300` и `ETag` (повтор — `304`) | `DL_UI_RATE_PER_MIN` |

| Столбцов в файле; строк | 200; строк не больше `DL_MAX_BATCH` (бланк одного анализа — 400) | в коде (`io/table.py`, `service.py`) |
| XLSX в распакованном виде | 50 МБ (бланк одного анализа — 5 МБ) | в коде (`service.py`) |

Превышение размера — `413`. Превышение лимита запросов — `429` с заголовком `Retry-After`.
Пределы кабинета — в разделе «Личный кабинет», «Пределы».

Адрес для лимитов — адрес соединения; IPv6 — сеть `/64`. `X-Forwarded-For` учитывается только от прокси,
перечисленных в `DL_TRUSTED_PROXIES` (по умолчанию — ни от кого), иначе подставной заголовок давал бы каждому
запросу «новый адрес». Лимиты хранятся в памяти процесса: перезапуск их обнуляет.

Размер тела проверяется и по заголовку `Content-Length`, и по фактически прочитанным байтам.
Вложенность JSON — не глубже 32 уровней (глубже — `422 invalid_json`, а не `500`).

Файл разбирается только как таблица (CSV, XLSX), как текстовый слой PDF или как изображение (Pillow
с ограниченным списком форматов JPEG, PNG, WEBP). Скрипты страницы вставляют данные
в страницу только как текст (в `static/*.js` нет вставки HTML из данных).
В выходном CSV все ячейки в кавычках, а ячейки, которые начинаются с `=`, `+`, `-`, `@`, табуляции или перевода
строки (в том числе после пробелов и в полноширинном написании), экранируются апострофом: так файл безопасно
открывать в Excel.

## Заголовки ответа

На каждом ответе:

| Заголовок | Значение |
|---|---|
| `Content-Security-Policy` | `default-src 'self'; img-src 'self' data: https://tile.openstreetmap.org; frame-ancestors 'none'; base-uri 'none'; form-action 'self'` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `no-referrer` |
| `X-Frame-Options` | `DENY` |
| `Cross-Origin-Resource-Policy` | `same-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(self)` — положение только для своей страницы («Где сдать рядом») |
| `Cache-Control` | `no-store` для `/api/`, `/ui/`, `/healthz` (кроме справочника `GET /ui/reference`, `/ui/examples` — `public, max-age=300` и `ETag`); статика с меткой версии `/static/*?v=…` — `public, max-age=31536000, immutable` (метка — хеш содержимого всех файлов `static/`, меняется с любым файлом); шрифты `/static/fonts/` — `public, max-age=604800`; остальное (страницы, статика без метки, ошибки) — `no-cache` |
| `Strict-Transport-Security` | `max-age=31536000` — только при `DL_COOKIE_SECURE=1` (сайт за HTTPS) |

Политика CSP не разрешает встроенные скрипты и стили: всё грузится файлами со своего адреса.

Сжатие `gzip` (от 1 КБ) — только для статики, HTML-страниц, `/api/v1/openapi.json` и справочника страницы: в них нет
данных пользователя. Ответы с персональными данными (`/api/v1/me*`, `/api/v1/auth*`, кабинет врача, расчёты
`/api/v1/*` и `/ui/*`) не сжимаются: сжатый ответ, где секрет соседствует с тем, что может подставить чужая
страница, выдаёт содержимое по длине (BREACH). Список сжимаемых путей — разрешающий (`security.gzip_allowed`).

Неизвестный адрес: браузеру (`Accept: text/html`, путь не под `/api`, `/ui`, `/static`) — страница `404.html`
со ссылкой на главную (адрес из запроса в неё не попадает), остальным — JSON `404 not_found`. Любое необработанное
исключение — и в обработчиках, и в обёртках, и в `StaticFiles` — ответ `500 internal` в JSON без трассировки;
в журнал — только тип исключения и место (файл:строка).

## Нет внешних вызовов

- Код сервиса не делает исходящих сетевых запросов. Внешних API и языковых моделей нет.
- Фото бланка распознаёт Tesseract внутри контейнера (пакеты Debian `tesseract-ocr`, `-rus`, `-eng`);
  облачного OCR и языковых моделей нет (ADR 0007).
- Страница не использует CDN, внешние шрифты, счётчики и аналитику. Скрипты и стили лежат в `static/`
  (шрифт IBM Plex и Leaflet — свои копии).
- Единственное, что страница грузит снаружи, — картинки подложки карты `tile.openstreetmap.org` в блоке
  «Где сдать рядом», и только после нажатия «Выбрать на карте» (ADR 0008). Им уходит только origin страницы;
  значения анализов и координаты человека не уходят. Сервер OSM видит, какой район карты открыт.
- Положение человека (кнопка «Определить моё положение» или щелчок по карте) обрабатывается только в браузере:
  ближайшие пункты считаются по своему списку `static/labs/labs_msk.json`; координат нет ни в запросах к сервису,
  ни в ссылках на Яндекс Карты (поиск — по названию анализа, маршрут — до координат пункта).
- Отчёт DOCX собирается в браузере (`static/export.js`), PDF — окном печати браузера; на сервер отчёт не уходит.
- Выводы строят правила и модели, тексты — шаблоны из `config/texts_ru/`.

Значит, значения анализов не покидают машину, на которой запущен сервис, а положение человека — его браузер.

## Развёртывание в контуре клиники

Сервис можно запустить внутри сети организации, без доступа в интернет: для работы он не нужен.
Интернет нужен только при сборке образа (базовый образ и пакеты Python).

Что задано в `Dockerfile` и `docker-compose.yml`:

- процесс работает от пользователя без прав root;
- файловая система контейнера только для чтения (`read_only: true`); для записи доступен только `/tmp` в памяти;
- один том с данными — `jm-data` (`/data`, база личного кабинета); других нет;
- сняты все привилегии ядра (`cap_drop: ALL`), запрещено повышение привилегий (`no-new-privileges`);
- порт по умолчанию открыт только на локальном адресе `127.0.0.1`;
- в образ не попадают файлы кейса и NHANES (`.dockerignore`).

Проверено на работающем контейнере (Docker 29.7.2, Compose v5.3.1, macOS arm64):
процесс работает с uid 10001, запись в `/app` отклоняется («Read-only file system»), `/tmp` — tmpfs 128 МБ,
`docker diff` после запросов пуст. На amd64 образ не собирался.

Что нужно добавить при развёртывании в сети организации:

1. Шифрование канала (TLS) на обратном прокси. Сам сервис работает по HTTP. За HTTPS — `DL_COOKIE_SECURE=1`
   (cookie `__Host-jm_session` с `Secure`).
2. Свой ключ API вместо демо-ключа; выдача ключа каждой системе-клиенту.
3. Закрыть страницу демо и маршруты `/ui/*` входом или сетевыми правилами: сейчас они открыты.
4. Если сервис стоит за прокси, укажите его адрес или сеть в `DL_TRUSTED_PROXIES` (например `172.16.0.0/12`
   для прокси в соседнем контейнере): тогда лимиты считаются по адресу клиента из `X-Forwarded-For`, а проверка
   `Origin` — по схеме и хосту из `X-Forwarded-Proto` / `-Host`. Прокси должен перезаписывать эти заголовки
   (nginx: `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; X-Forwarded-Proto $scheme;
   Host $host`). Без настройки все клиенты делят адрес прокси — лимит ставится и на прокси. Доверяйте сети
   прокси, только если порт сервиса доступен лишь прокси (`DL_PUBLISH=127.0.0.1:8080`): соединения с хоста
   приходят в контейнер с адреса шлюза Docker, и при порте, открытом в сеть, с этого адреса мог бы прийти
   и посторонний клиент со своим `X-Forwarded-For`.
5. Ключ шифрования кабинета — `DL_DATA_KEY` из хранилища секретов или `DL_DATA_KEY_FILE` (файл `0600`
   вне тома `jm-data`); предел базы — `DL_DATA_MAX_MB`, регистраций в сутки — `DL_MAX_SIGNUPS_PER_DAY`.

## Публикация по ссылке

Публичная ссылка на демо — только на сервере команды. Перед выкладкой проверьте пять пунктов.

1. **Свой ключ API, не демонстрационный.** Демо-ключ `dl-demo-key` записан в `docker-compose.yml` и известен
   всем, кто видел репозиторий. Задайте свой в `DL_API_KEYS` (через запятую, если ключей несколько).
   Если работает и мини-сайт клиники, передайте ему тот же ключ в `DL_CLINIC_API_KEY`.
2. **Лимит запросов включён.** Лимит страницы демо работает всегда; число задаёт `DL_UI_RATE_PER_MIN`
   (по умолчанию 30 в минуту с адреса). То же число ограничивает тяжёлые запросы `/api/v1/*` на ключ.
   За прокси задайте `DL_TRUSTED_PROXIES` (см. п. 4 выше), иначе лимит общий для всех посетителей; лимит
   по адресу клиента полезно поставить и на прокси.
   Для кабинета за HTTPS — `DL_COOKIE_SECURE=1`, ключ — `DL_DATA_KEY` или `DL_DATA_KEY_FILE` (не демо-ключ
   в томе с базой).
3. **На странице есть строка «Не вводите персональные данные».** Она в шапке каждой страницы
   (`templates/base.html`: «Демо. Не вводите персональные данные. Не медицинское изделие.»).
4. **Сервис наружу не ходит.** Исходящих запросов, CDN, внешних шрифтов и счётчиков нет (см. «Нет внешних
   вызовов»); CSP `default-src 'self'` не даст странице загрузить чужой ресурс — кроме картинок подложки карты
   `tile.openstreetmap.org` по кнопке «Выбрать на карте». Геолокация в браузере работает только по HTTPS
   (или на `127.0.0.1`), то есть за прокси с TLS.
5. **Порт и TLS.** Порт публикуется переменной `DL_PUBLISH` (по умолчанию `127.0.0.1:8080` — только эта машина).
   Если прокси стоит на том же сервере, оставьте `127.0.0.1:8080` и направьте прокси на этот адрес;
   `DL_PUBLISH=0.0.0.0:8080` открывает порт в сеть без шифрования. TLS включается на обратном прокси сервера
   команды: сам сервис работает по HTTP.

Команда на сервере (каталог — корень репозитория):

```bash
DL_API_KEYS='<свой ключ>' DL_PUBLISH=127.0.0.1:8080 DL_COOKIE_SECURE=1 DL_TRUSTED_PROXIES=172.16.0.0/12 \
  DL_DATA_KEY='<ключ Fernet>' docker compose up -d --build
```

Вместо `DL_DATA_KEY` можно задать `DL_DATA_KEY_FILE` — путь к файлу с ключом (права `0600`, не в томе `jm-data`).
`DL_TRUSTED_PROXIES` — адрес или сеть своего прокси (см. п. 4 раздела «Развёртывание в контуре клиники»).

Проверка после выкладки: `curl -s https://<адрес>/healthz` → 200; `POST /api/v1/analyze` без ключа → 401,
с ключом `dl-demo-key` → 403.

## Чего нет

| Чего нет | Почему или что это значит |
|---|---|
| Входа через внешнего поставщика (Госуслуги / ЕСИА), второго фактора, восстановления пароля | В кабинете — только логин и пароль (ADR 0009); страница демо без входа открыта |
| Разграничения по организациям, ролей кроме «пациент» и «врач» | Врач видит только пациентов, открывших ему доступ по ссылке |
| Резервных копий базы кабинета | Удалённое не восстанавливается; том `jm-data` — единственная копия |
| Шифрования всего тома и управления ключами (KMS, HSM) | Шифруются поля с данными анализов; ключ — переменная окружения, файл-секрет (`DL_DATA_KEY_FILE`) или файл рядом с базой (демо) |
| TLS | Нужен обратный прокси |
| Полного журнала действий пользователей (аудита) | Есть технический журнал запросов и журнал доступа врачей к данным пациента (его видит пациент) |
| Отзыва и смены ключа без перезапуска | Ключи читаются из окружения при старте |
| Лимита для лёгких запросов `/api/v1/analyze`, `/api/v1/reference` | Лимит на ключ есть только у тяжёлых запросов (batch, benchmark, columns, parse); у загрузки в кабинет (`me/import`) — на пользователя |
| Лимита по ключу, квот, учёта использования | Не сделано |
| Проверки на вредоносные файлы | Файл читается только как таблица; исполняемое содержимое не запускается |
| Обезличивания входных данных | Сервис ожидает уже обезличенный ввод |
| Анализа защищённости и нагрузочных тестов | Не проводились |

## Что нужно для промышленного использования

Это направления работы, а не обещания. Ничего из перечисленного в прототипе нет.

**152-ФЗ «О персональных данных».** Результаты анализов конкретного человека — сведения о состоянии здоровья,
то есть специальная категория персональных данных. Без входа сервис получает только пол, возраст и значения
без идентификаторов и ничего не хранит — значит, не связывает значения с человеком. Как только сервис подключают
к системе клиники, где запрос можно связать с пациентом, появляются обязанности оператора: правовое
основание обработки, модель угроз, меры защиты, размещение на территории России, порядок доступа
и учёт действий. Это решается вместе с юристом и службой безопасности организации.
Личный кабинет (ADR 0009) уже связывает значения анализов с учётной записью. Это прототип, а не система,
соответствующая 152-ФЗ: нет формального согласия на обработку специальных категорий ПДн, резервных копий,
разграничения по организациям, аттестации. Реальные данные в кабинет не вводить.

**Регистрация как медицинского изделия.** Программа, которая по данным пациента выдаёт сведения для
диагностики, по назначению относится к программному обеспечению — медицинским изделиям. Прототип
не зарегистрирован и для решений о пациентах не применяется. Для работы в клинике нужны: клиническая
проверка на данных этой клиники, техническая документация, управление рисками и регистрация
в Росздравнадзоре. Сроков и результата мы не обещаем.

**До этого возможен только режим «в тени».** Сервис считает на ретроспективной обезличенной выгрузке,
результаты сравниваются с фактическими диагнозами и не влияют на назначения.
